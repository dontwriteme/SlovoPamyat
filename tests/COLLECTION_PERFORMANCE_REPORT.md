# Открытие коллекций: профиль и оптимизация

Измерения сделаны в одной облачной среде, Robolectric API 28 с **нативной SQLite**, JDK 17. Это не физический Android и не измерение FPS. Ориентир тёплого открытия ≤300 мс на устройстве **не подтверждён**.

## Причина задержки

`renderUnifiedCollectionDetail()` синхронно вызывал `studyProgressFor()` и `entryCard()`. Оба пути повторно выбирали каноническую запись и считали прогресс. `masteryCount()` и `consolidatedVerseCount()` обходили стихи, а `matchingVerseLocations()` для каждого стиха выполнял `allEntries()` и разбирал JSON всех отрывков. `canonicalStudyEntryId()` дополнительно запускал эти обходы для каждой полной копии отрывка. Это выполнялось на UI-потоке.

`syncUnifiedCollection()` не вызывается непосредственно из detail render: он запускается загрузчиком Библии и при старте режимов. Однако его повторный вызов проверял каждую связь отдельным SELECT; первая синхронизация ещё и перечитывала всю колоду после добавления каждого стиха.

## Условия и сравнение

Размеры: 1, полное Послание к Галатам (149), 550 строк (Галатам циклически повторено). У каждого отрывка есть идентичная копия в другой коллекции с освоенным первым стихом. В одном тесте размеры добавляются последовательно: база на следующем размере содержит предыдущие коллекции. До/после условия одинаковы. Два последовательных прохода: 0 — первый после добавления данных; 1 — повторный. Это не холодный дисковый кэш ОС.

Время отдельных этапов измерено `System.nanoTime()`. Счётчик охватывает SELECT/PRAGMA, проходящие через `LocalStore.readQuery`. Для путей открытия он учитывает все чтения LocalStore. Для синхронизации это **частичный счётчик**: внутренние запросы через переменную `db` в addFlashcard, SQL-записи и скрытые SQLite-операции не включены. Количество записей не заявляется измеренным.

## Реализация и совместимость

- `CollectionProgressSnapshot` один раз декодирует записи, индексирует совпадения по ref + точному тексту и пакетно читает освоение, закрепление, упражнения, связки и порядок. Критерий совпадения сохранён как в исходном коде: только записи с библейским названием; пользовательские тексты исключены. Прежнее поведение одинаковых ref/text между библейскими книгами не изменялось.
- Сохраняются правила выбора канонической полной копии: mastery × 10 + сумма упражнений, при равенстве меньший id. Совпадающие позиции внутри той же записи сами себе прогресс не передают.
- Пакет строится в транзакции. Кэш проверяется по total_changes на закреплённом основном подключении и PRAGMA data_version для внешних подключений. Внутри незавершённой транзакции результат не публикуется в кэш; откат не оставляет ложного прогресса. Если SQLite-обёртка не возвращает маркер, применяется безопасное перечитывание без использования кэша.
- На каждый обычный render не повторяются пакетные SELECT и декодирование: остаются две дешёвые проверки актуальности в фоне. После записи прогресса/изменения материалов пакет перестраивается.
- Отдельный последовательный Executor загружает коллекции. UI получает результат только для актуальных поколения, collection id и контейнера. Закрытие БД поставлено после выполняющегося чтения, уничтоженная Activity не обновляется.
- Большие списки добавляются по 12 карточек за кадр, с проверкой актуальности каждого блока и восстановлением прокрутки после завершения. Отрисовка не делает запросов за каждой карточкой.
- Синхронизация загружает связи и содержимое коллекции один раз, затем использует множества. Поиск созданной карточки идёт по существующему UNIQUE-индексу её канонических координат. Ошибки обработки legacy-карточки регистрируются.
- Имя БД, версия схемы (8), таблицы, алгоритмы повторений, тексты и дизайн не менялись. Чтение пакета не пишет прогресс.

## Проверки и воспроизведение

```bash
source /workspace/toolchains/env.sh
gradle --daemon --max-workers=4 -I tests/validation.init.gradle -x :app:createSynodalSearchIndex :app:assembleDebug :app:testDebugUnitTest --tests org.biblememory.app.CollectionPerformanceTest --tests org.biblememory.app.CollectionProgressSnapshotTest --tests org.biblememory.app.CollectionLoadingTest
```

Профили печатаются в system-out XML результатов JUnit. Наборы проверяют размеры, совпадения между коллекциями, пользовательские тексты, изменения текста, порядок, инвалидирование другим SQLiteOpenHelper, успешную транзакцию и откат, сохранность расписания и истории, идемпотентную синхронизацию и восстановление удалённой связи карточки. UI-тесты проверяют открытие/возврат, запуск изучения, запоздалый результат и дозированное создание большого списка.

## Ограничения

- Нативное устройство/эмулятор, StrictMode, Choreographer frame timing и системный профилировщик в этом измерении не использовались. Цель 300 мс необходимо проверить на целевом телефоне с его реальной базой.
- Общий индекс имеет линейный размер относительно всей локальной библиотеки; память и время для десятков тысяч сохранённых отрывков не измерялись.
- Большой список всё ещё создаёт все View, хотя по порциям. Потребление памяти большого списка не профилировалось.
- Холодная синхронизация всё ещё выполняет необходимые записи на каждый стих. Не добавлялись постоянные SQL-индексы или миграции.
- Полный общий набор содержит известные сбои PickerIntegrationTest; детали фактических запусков приведены ниже.


### Фактические результаты проверок

- `CollectionPerformanceTest`: 2 теста прошли (1/149/550 строк и 550 отдельных записей).
- `CollectionProgressSnapshotTest`: 4 теста прошли (общий прогресс, обновление через другое подключение, порядок, сохранность расписания/истории, откат, совпадения и синхронизация).
- `CollectionLoadingTest`: 3 теста прошли с прикреплённым окном. Все 550 карточек добавлены, дополнительных чтений БД при добавлении порций нет; переход на другой экран защищён от запоздалого результата.
- `LessonHotbarIntegrationTest`: 14 существующих тестов прошли после исправления совместимости с SQLite-обёрткой тестов, которая возвращает пустой PRAGMA data_version.
- Общий промежуточный запуск: 96 тестов, 17 сбоев; 14 из них вызваны указанным пустым PRAGMA, исправлены и перепроверены адресно. Оставшиеся 3 — прежние сбои `PickerIntegrationTest`: поиск/очистка и back stack сетки стихов. Полный набор после адресных исправлений повторно не запускался и не объявляется зелёным.
- Итоговая `assembleDebug` успешна, подпись APK проверена. `check_bible_grids.py` и `git diff --check` прошли.
- Продолжительность внутренних `matchingVerseLocations()` и `isStepMastered()` включена в измеренные родительские операции; отдельное exclusive-время этих методов не измерялось.

Изменённые файлы: `LocalStore.java`, `MainActivity.java`; добавлены
`CollectionProgressSnapshot.java`, три указанных тестовых класса, этот отчёт и CSV замеров.
